# ChatServe

一个从 epoll 手写起的多人在线聊天服务器。

**不依赖任何第三方库** —— 事件循环、HTTP / WebSocket 协议解析、线程调度、文件传输全部自建，连 WebSocket 握手用的 SHA1 也是自己实现的。

配套 Vue 3 前端与 Electron 桌面外壳。C++17，服务端约 5100 行，前端约 1700 行，单元测试 97 个用例。

## 功能

| 功能 | 说明 |
| --- | --- |
| 实时聊天 | 房间制，单房间最多 9 人，成员进出广播，消息走 WebSocket 全双工 |
| 文件传输 | 应用层滑动窗口，分块 256KB、窗口 8，逐块 ACK，支持断点续传 |
| WebRTC 音视频 | 服务器只中转信令，媒体流走浏览器 P2P 直连 |
| HTTP 服务 | 前端页面与静态资源，含路径穿越防护 |
| 桌面客户端 | Electron 外壳，可打包为单文件 exe |

## 整体架构

### 分层与依赖

依赖严格单向：

```
core          事件循环、线程池、定时器、跨线程队列    根，无内部依赖
  ↑
ctrl          Session 控制块、跨线程消息、邮箱
  ↑
chatroom      房间与房间内的文件传输
  ↑
app           应用层命令路由与业务处理

http          HTTP 解析、路由、静态文件              无内部依赖，与 core 并列
  ↑
ws            WebSocket 帧层与握手，依赖 http

conn          连接泵：读缓冲、分帧、施加决策
              依赖 core / ctrl / http / ws
  ↑
server        装配层：Reactor、网关、中控、工厂
              依赖其余全部
```

**头文件一律直接 include 所需类型**，不靠传递包含。

### 线程模型

```
                    ┌──────────────┐
   accept ─────────▶│  主 Reactor  │  fd % N 哈希分发
                    └──────┬───────┘
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
   ┌────────────┐   ┌────────────┐   ┌────────────┐
   │ io 从属 0  │   │ io 从属 1  │   │ io 从属 N  │   各一条线程
   │ Connection │   │ Connection │   │ Connection │
   └─────┬──────┘   └─────┬──────┘   └─────┬──────┘
         │  CtrlUp        │  CtrlUp        │  CtrlUp
         └────────────────┼────────────────┘
                          ▼
                  ┌───────────────┐
                  │   中控线程    │  唯一分发点 + 业务串行门
                  └───────┬───────┘
                          ▼
                  ┌───────────────┐
                  │  业务线程池   │  AppRouter 命令表
                  └───────────────┘
```

四个执行体：主 Reactor、N 个 io 从属、一条中控线程、一个业务线程池。

### 一条消息的完整路径

```
io 线程      收字节 → 读缓冲 → 协议解析 → 组出上行事件
                 ↓ 跨线程邮箱
中控线程      串行判定 → 攒满一批投进业务池
                 ↓
业务线程池    命中命令表 → 算出待发帧
                 ↓ 跨线程邮箱
中控线程      整批分拣 → 按会话归属投回各 io
                 ↓ 跨线程邮箱
io 线程       组帧 → 排空待写缓冲
```

## 关键设计

**io 与业务分离。** io 只做 socket 生命周期 —— 收字节、分帧、组帧、写；业务全在独立线程池，io 线程不被业务的计算量拖住。

**主从 Reactor：连接归属在 accept 时定死，之后不再变。** 一条 io 线程扛不住连接数，而把一条连接的读写分到两条线程就会引入跨线程状态。accept 是唯一零成本的时刻 —— 那时连接还没有任何状态，也没注册进 epoll；等这些长出来再改归属，就得跨线程搬或者上锁。所以主 Reactor 只监听 accept，按 fd 取模把连接分给 N 个从属，各跑各的事件循环，归属就此定死 —— 此后一条连接的全程落在一条线程内，读缓冲、待写字节、epoll 注册都由它独占。

**中控线程居中：io 之间、io 与业务之间都不直连。** 一条消息常常要写到别的连接上，而那些连接可能在别的 io 线程 —— 房间广播、信令中继都是，io 侧本来就要跨线程。没有中控，每个 io 都得认识所有别的 io 和整个业务侧，成了 N×N 直连；立一条中控居中，io 的跨线程面就只剩两个邮箱 —— 自己建的下行邮箱，和一条上行邮箱的引用，它拿不到中控，也拿不到线程池，也拿不到别的 io。反向也一样，中控手里只有每个 io 的下行邮箱和业务处理段；跨线程往返因此只剩它这唯一一个出口。

**邮箱解耦：发送方不再认识消费方 —— 两边只共认一份消息类型，处理入口由消费方自绑。** 直接互调方法会把两边绑死，改一边另一边得跟着动。所以跨线程一律走邮箱 —— 邮箱由消费方自己创建，构造时把自己的处理入口绑进去，发送方只投类型化数据。事件循环本来也能投闭包，但那要求发送方说清「到对面执行什么」，等于认识对面的入口。

**单飞门：同一连接的命令串行执行。** 一条连接的两条命令可能改同一份状态，并发跑就会读到中间态。单飞门让同一会话至多一条命令在业务池中，后续排队，业务完成后中控再拉下一条；连接关闭也走这道门，收尾排在在途业务之后。于是顺序整段收在中控 —— 业务处理器只管拿会话算响应，连有没有在途命令都不必知道，也不必为它加锁。

**两个方向都攒批，交界按批算不按条算。** 逐条投递是每条一次加锁加一次系统调用，消息量上来后全耗在这上面。上行一轮排空攒出整批命令、末尾一次投进池；回程池线程算完整批投回中控，中控合起来分拣一次，再按会话归属投回各 io。队列排空在途时生产方只追加，不重复唤醒。

**锁还是无锁，看访问粒度：逐条取用的队列走无锁，整批交接的队列用一把锁。** 池线程每次只领一条任务，无锁环形队列每条一次 CAS，省掉每次取任务过一遍互斥量、以及唤醒全部池线程的惊群。邮箱那头正相反 —— 交接本来就是整批的，加锁、两个 vector 互换指针、解锁，临界区与批大小无关；要无锁化就得逐条取出来攒批，把 O(1)/批 赔成 O(N)/批。

**跨线程共享的只有一块会话控制块，里面没有一样东西被两条线程同时写。** 业务要读连接的房间，中控要按归属把下行帧投回去，而任务排队期间连接可能已经断开、fd 可能已经分给别人。所以共享状态收进一块控制块：引用计数保活，身份就是对象本身而不借 fd；身份与归属构造后只读，存活由 io 独占写、别处只读，房间只由该会话自己的业务读写 —— 而同会话的业务被单飞门串行。于是一张表都不用建。

## 构建与运行

需要 CMake ≥ 3.14 与支持 C++17 的编译器。**一条命令跑起来**：

```bash
./scripts/run.sh          # 构建 + 起服务，证书齐全时顺带拉起 HTTPS 代理
```

浏览器打开 `http://localhost:8080/chat`，开两个标签页各填一个昵称、进同一个房间，就能看到聊天与成员广播；点输入框左侧的回形针发文件。视频通话需要 HTTPS，见下。默认监听 8080，io worker 数量在 `server/main.cpp` 的 `kIoCount` 调整。

不用脚本时，等价的两步是 `./build.sh` 构建、`./build/server/chat_server` 起服务。

**单元测试**（97 个用例，覆盖协议解析、连接处理、缓冲、命令路由、业务处理段、传输窗口、心跳判据、攒批与无锁队列、周期节拍）：

```bash
./build/test/chat_tests     # 直接跑，逐条打印结果
cd build && ctest           # 或走 CTest
```

压测另有三个可执行：`chat_bench` 消息中继、`chat_transfer_bench` 并发传输、`chat_queue_bench` 任务队列对拍。

**HTTPS 代理**（WebRTC 的摄像头麦克风只在安全上下文可用，所以需要 TLS）：

```bash
python3 scripts/https_proxy.py      # 8443 → 8080
```

浏览器访问 `https://<本机 IP>:8443/chat`，首次需要手动信任自签证书。

仓库只带了 `scripts/cert.pem`，**私钥不随仓库分发**（`run.sh` 检测到缺私钥会跳过代理）。自己签一对：

```bash
openssl req -x509 -newkey rsa:2048 -nodes -days 3650 \
  -keyout scripts/key.pem -out scripts/cert.pem -subj "/CN=chatserve"
```

**前端**：

```bash
cd web && npm install && npm run build   # 产物输出到 ../static
```

**桌面客户端**：

```bash
cd client && npm install && npm run dist  # 产出 dist/ChatServe.exe
```

服务器地址可配置，优先级：`--server=<地址>` 参数 → `CHATSERVE_SERVER` 环境变量 → 内置默认。

## 通信协议

应用层是自定义文本协议，`|` 分隔：`COMMAND|param1|param2|...`

**客户端 → 服务端**

| 域 | 命令 |
| --- | --- |
| 房间 | `JOIN` |
| 聊天 | `MSG` |
| 信令 | `OFFER` `ANSWER` `ICE` `MEDIA` |
| 传输 | `UPLOAD` `UPCANCEL` `DOWNLOAD` `DWACK` `DWNPAUSE` `DWNCANCEL` |
| 心跳 | `PING` |

**服务端 → 客户端**

| 域 | 帧 |
| --- | --- |
| 房间 | `OK` `SYS` `MEMBERS` `JOIN` `LEAVE` |
| 聊天 | `MSG` |
| 信令 | `OFFER` `ANSWER` `ICE` `MEDIA` |
| 传输 | `UPOK` `FILE` `DONE` `DWSTART` `DWREQ` `DWERR` `DWDATA` `DWNDONE` |
| 心跳 | `PONG` |

无 `|` 的裸文本与未注册命令一律丢弃。

**心跳是连接存活的唯一凭据。** 客户端每三十秒发一条 `PING|`，服务端原样回一条 `PONG|`，两条都走数据帧 —— 浏览器的 WebSocket API 不给控制帧留接口。服务端不做主动探测，只按活跃度判死：升级过的连接只认入站字节，静默满九十秒就收掉，客户端不起搏就不会被保活；未升级的 HTTP 连接收完请求行就没有入站，出站写成功也算它活跃，否则慢链路上下一份大文件会被误杀。

**文件分块**走 WS 二进制帧，载荷前 20 字节是固定头，其余为文件数据：

```
[session_id:8 LE][offset:8 LE][data_size:4 LE][data...]
```

**传输流程**：下载方向上传方发起 `DWREQ` → 上传方按请求回分块 → 服务器转发给下载方 → 下载方 `DWACK` 确认 → 服务器补发下一个请求。窗口 8 块 × 256KB，`start_offset` 支持断点续传。

## 性能

同机 WSL2 16 核回环实测，压测程序在 `test/` 下。

**消息中继**（50 对连接，单条正文 204B）：约 **100 万条/s**。测试条件是客户端绑到 8~15 核、服务端不绑，每发送方限速 20000 条/s，每轮重启服务端。五十个发送方的限速总额恰好就是 100 万/s，所以这个读数卡在限速上，完成率到 100 万仍是 101%，越过它的平台天花板还没标定。换成无锁任务队列之前，同一条件只能做到约 46 万条/s。

**文件传输**（每房间一上传方一下载方，分块 256KB，窗口 8）：

| 场景 | 聚合吞吐 |
| --- | --- |
| 1 房间 × 256MB | 1010 MB/s |
| 8 房间 × 64MB | 2270 MB/s |
| 16 房间 × 64MB | 2392 MB/s |
| 32 房间 × 64MB | 2528 MB/s |

全部 100% 完成、零失败。这是客户端与服务端同机跑出来的联合结果，只适合与自身历史版本对比。

## 范围与定位

以下是有意为之的边界，不是缺口：

- **单机、纯内存中转**。消息不落库，重启即丢；房间不跨进程或跨机。文件传输全程滑动窗口，服务端一个字节都不落盘 —— 没有临时文件，也不存在落盘残留，这也是那份吞吐数字的前提
- **无认证，威胁模型是可信局域网**。知道房间名即可加入，用户名是显示名不是身份。它一旦对着公网就不再是范围问题
- **无 TLS**。明文 `ws://` / `http://`。WebRTC 要求安全上下文，本地演示靠 `scripts/https_proxy.py` 在服务外终结 TLS

## 已知限制与待办

- **无连接数上限**。连接数不受限，只靠心跳回收死连接，正常连接能一直占着 fd 与内存
- **无背压**。上行邮箱不设上限，中控排不过来时内存持续增长，极端情况下会被内核 OOM 杀掉；下行有每连接 16MB 上限兜底，上行什么都没有
- **大帧会阻塞同连接的后续帧**。WS 不允许帧交错，二进制分块发到一半时后到的文本帧只能排在它之后，发送队列是单一 FIFO，不做优先级调度
- **测试只覆盖纯逻辑**。连接建立、线程交互、WebRTC 信令这些跨单元的部分没有自动化测试，靠手工验证
